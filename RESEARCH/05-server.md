## 0. Вывод (коротко)

1. **Один новый Worker `pet-sync`** на том же аккаунте Cloudflare, где живёт Блок Дуо. Блок Дуо не трогаем, берём из него паттерны.
2. **Хранилища:**
   - **Durable Object `Account` на SQLite**, один на владельца. В нём устройства, питомец (живой и альбом памяти), журнал событий, кошелёк, инвентарь, инбокс, права передержки. DO обрабатывает запросы строго по одному, поэтому айфон и ПК не могут записать одновременно. Это закрывает вопрос конфликтов.
   - **D1** (одна база `pet-db`) для всего, что видно другим аккаунтам: справочник аккаунтов и кодов друзей, поиск по имени, граф дружбы, рекорды, версии конфига экономики, аналитика. Плюс D1: SQL-консоль и `wrangler d1 execute`, удобно смотреть аналитику раз в неделю.
   - **KV не используем** для состояния: на бесплатном плане 1 000 записей в день, и данные расходятся по краям с задержкой. KV — только запасной склад ассетов, если R2 недоступен.
   - **Ассеты:** встроенные персонажи и шмотки лежат статикой Worker'а (бесплатно). Свои загруженные персонажи хранятся в **R2**, если к аккаунту привязана карта. Если карты нет, то в **KV** (значение до 25 МиБ, 1 ГБ всего). Адресация по SHA-256.
3. **Бесплатных лимитов хватает с запасом примерно в 20 раз** на 10 человек (расчёт в §1.3). Главное условие: WebSocket только через Hibernation API, как в Блок Дуо.
4. **Синхронизация:** офлайн-первая, на сервер уходят только **действия** (event log) с id `deviceId:seq`. Сервер детерминированно сворачивает их в состояние. Два правила порядка:
   - **ресурсы** (монеты, предметы, покупки) — в порядке прихода на сервер;
   - **шкалы** (голод, гигиена, сон, ласка) — в порядке «эффективного времени» события.
5. **Время:** источник истины — серверное. Клиент ставит событию метку по якорю «серверное время + монотонные часы устройства» (`mach_continuous_time` на iOS, `QueryInterruptTime` на Windows). Подкрутка часов в настройках на метку не влияет. Сервер дополнительно зажимает время событий в окно «после прошлого синка этого устройства, но не позже прихода».
6. **Аутентификация без паролей:** ключ **P-256 ECDSA** на устройство (CryptoKit, по желанию Secure Enclave; на Windows CNG/.NET), подпись каждого запроса.
   - Защита от повторов: окно ±5 минут плюс идемпотентные id у всех изменяющих операций.
   - Виджету отдельный **read-only токен**, ключ ему не нужен.
   - Второе устройство привязывается кодом или QR с подтверждением на первом.
   - Если потеряны все устройства, выручает **код восстановления**.
   - Регистрация только с инвайт-кодом, чтобы сервер не заспамили чужие.
7. **Социалка без пушей:**
   - один эндпоинт `/v1/sync` отдаёт и состояние, и инбокс;
   - виджет дёргает крошечный `/v1/w/<токен>`;
   - ПК держит гибернируемый WebSocket и получает изменения сразу;
   - задержку оформляем как механику: питомец-почтальон, «📬 2» в виджете, отметки «доставлено / увидел».
8. **Смерть честная.** Сердечки считает сервер (DO alarm), но смерть финализируется только после «окна оправданий». Если пришло офлайн-событие, сделанное до смерти, состояние пересчитывается и питомец спасён.

**Откуда ~5 000 запросов в день.** Оценка на одного человека:
- приложение: открытия + фоновое обновление ≈ 30 запросов `/v1/sync`;
- виджеты: ≈ 100 запросов `/v1/w` (iOS сам ограничивает обновления, обычно 40–70 на виджет, а виджетов 2–3);
- ПК: WebSocket с гибернацией. Сообщения считаются 20:1 и не будят DO на ping (`setWebSocketAutoResponse`), плюс ~50 запросов `/v1/sync` при действиях;
- игры, друзья, аналитика: ~30.

Итого ~200–450 запросов на человека, то есть ~2–5 тыс. на 10 человек.

**Главный пожиратель лимитов** — WebSocket через `accept()` без гибернации. Он тарифицирует всё время соединения: ПК, подключённый на 8 часов, съест ~3 700 GB-s, это 28 % дневного лимита. Поэтому только `ctx.acceptWebSocket()`, как в Блок Дуо.

**Если упрёмся в лимиты.** Workers Paid стоит $5 в месяц и снимает дневные лимиты. При офлайн-первой модели даже исчерпание лимита не ломает игру: клиенты копят события и досылают их после 00:00 UTC.

## 2. Модель синхронизации (офлайн-первая)

### 2.1 Принципы

- **Клиент — оптимист:** применяет действие локально сразу, кладёт событие в очередь `outbox`, шлёт при любой возможности. Источники отправки: приложение при открытии и в `BGAppRefreshTask`, интенты виджета и острова (если App Group работает — через общий outbox), ПК сразу.
- **Сервер — арбитр.** Состояние = детерминированная свёртка `fold(чекпойнт, события)`. Ответ сервера — правда. Клиент делает **rollback-and-replay**: берёт серверный снапшот на `rev` и проигрывает поверх свои ещё не подтверждённые события.
- **Ленивые шкалы:** в состоянии хранятся `value@ts` и текущие модификаторы (сон, болезнь, «будка»). Значение на момент `t` считается формулой по отрезкам день/ночь в часовом поясе питомца. Никаких тиков и cron'ов по шкалам.
- **Целочисленная математика:** шкалы 0..10 000, время в мс, скорости в «единиц на час × 1000». Без float, иначе Swift и TypeScript разойдутся в последних битах.
- **Одна логика, две реализации плюс общие тест-векторы.** `core/` на TypeScript на сервере, Swift на iOS, позже C# или TS на ПК. Плюс папка `vectors/*.json` вида «начальное состояние + события → ожидаемое состояние», их гоняют обе стороны в CI. Альтернатива — гонять тот же `core.js` на iOS через JavaScriptCore (точно идентично, но тащит JS в виджет). Решать на этапе 3; рекомендую векторы.

### 2.2 Формат события

```jsonc
{
  "id":   "dK3f9…:1842",        // deviceId:seq — глобально уникален, ключ идемпотентности
  "seq":  1842,                 // монотонный счётчик устройства (хранится в Keychain/файле, не сбрасывается)
  "v":    1,                    // версия схемы этого типа события
  "type": "feed",
  "pet":  "p_7Hq2…",
  "args": { "item": "iu_8f2c", "food": "bone_common" },
  "t": {                        // как клиент оценил время
    "est":  1792072800123,      // оценка серверного времени (см. 2.3) — главное поле
    "wall": 1792072799000,      // сырые часы устройства — только для диагностики
    "boot": "B-5c1e…",          // id сессии загрузки (iOS: sysctl kern.bootsessionuuid)
    "mono": 81234567890         // монотонные часы с учётом сна, мс
  },
  "cfg":  14,                   // версия экономики, по которой клиент предсказывал
  "rules": 3                    // версия правил симуляции клиента
```

**Типы событий.** Начальный список, расширяется:

| Группа | Типы | Порядок применения |

| Ресурсы | `buy`, `equip`, `unequip`, `place_furniture`, `upgrade_home`, `spin` (крутит сервер), `claim_daily`, `gift_send`, `inbox_claim`, `visit_send`, `poke` | по приходу |

**Ответ `/v1/sync`:**

```jsonc
{

  "rev": 5123,                  // ревизия состояния аккаунта
  "acks":     [{ "id": "dK3f9…:1842", "eff": 1792072800123 }],
  "rejected": [{ "id": "dK3f9…:1843", "why": "no_item" }],   // клиент откатывает и объясняет («шапку уже надели на ПК»)
  "state":    { /* снапшот ~3–6 КБ: питомец, шкалы value@ts, кошелёк, инвентарь, дом */ },
  "inbox":    [ /* новые сообщения от друзей */ ],
  "cfg":      { "v": 14, "etag": "W/\"14\"" },   // если у клиента старее — он тянет /v1/config
  "minClient": "0.3.0"          // ниже — клиент показывает «обнови сборку»
}
```

### 2.3 Время: серверное как источник истины

**На клиенте.** После каждого успешного запроса сохраняем якорь `{serverMs: now, mono: mono_now, boot: boot_id}`. Новые события получают метку:

```
est = (boot == anchor.boot)
      ? anchor.serverMs + (mono_now - anchor.mono)    // монотонные часы, подкрутка часов не влияет
      : wall_now + lastOffset                          // после перезагрузки — что есть, сервер зажмёт
```

Источники монотонного времени с учётом сна:
- iOS: `mach_continuous_time()` или `clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW)`;
- Windows: `QueryInterruptTime` / `GetTickCount64`.

`CLOCK_UPTIME_RAW` и `QueryUnbiasedInterruptTime` не подходят: они не считают сон.

**На сервере** (`effectiveTs`):

```
eff = ev.t.est
eff = min(eff, recvTs)                                  // из будущего нельзя
eff = max(eff, device.lastSyncRecvTs - SLACK_5s)        // раньше прошлого синка этого устройства нельзя: тогда бы оно его уже прислало
eff = max(eff, device.lastEff)                          // внутри устройства время не идёт назад (по seq)
eff = max(eff, recvTs - MAX_BACKDATE_72h)               // офлайн дольше 3 суток — старые события считаем «на 72 ч назад»
```

Итог: подкрутить часы вперёд, чтобы «домылось» или «прошли сутки для рулетки», нельзя.
- Все длительности (мытьё, сон, кулдауны, суточная рулетка, серии входов) сервер отсчитывает от `eff` и от своего `now`.
- `wash_end`, пришедший раньше `wash_start.eff + washDuration(cfg, buffs)`, применяется в момент окончания по серверу.
- Дневные границы (рулетка, ежедневки, серия) считаются по серверному времени в часовом поясе питомца. `tz_change` разрешён не чаще раза в 24 ч.

### 2.4 Два порядка: ресурсы и шкалы

**Проблема.** Айфон офлайн в 10:00 скормил «кость #8f2c», ПК онлайн в 10:05 скормил ту же кость. Если сортировать всё по времени, при позднем приходе айфона пришлось бы задним числом отменять уже подтверждённое событие ПК.

**Решение.**
- **Ресурсная часть** (списание монет и предметов, покупки, подарки, крутки) проверяется **в порядке прихода** и после `ack` **не пересматривается никогда**. Вторая попытка съесть тот же предмет получает `rejected: no_item`.
- **Эффект на шкалы** (сытость +X в момент `eff`) встраивается в кривую **по эффективному времени**. Поздний приход вызывает перемотку: берём ближайший чекпойнт до `eff`, проигрываем события заново. Ресурсные решения при этом не меняются, они уже зафиксированы.
- Взаимоисключающие состояния (уже моется, уже спит) идемпотентны: второй `wash_start` в пределах активного мытья → `ack` с пометкой `merged`.

```ts
// Account DO — сердце sync (псевдокод)
async sync(deviceId, events, sinceRev) {
  const dev = this.devices.get(deviceId)            // уже проверили подпись
  const recv = Date.now()
  this.sql.transaction(() => {
    for (const ev of events.sort(bySeq)) {
      if (this.events.has(ev.id)) { acks.push(prevAck(ev.id)); continue }   // повтор → тот же ответ
      const eff = effectiveTs(ev, dev, recv)
      const res = resourcePhase(this.state, ev, recv, cfgAt(recv))          // монеты/предметы: по приходу
      if (!res.ok) { reject(ev, res.why); continue }
      this.events.insert({ ...ev, eff, recv, status: 'applied', resDelta: res.delta })
      minEff = Math.min(minEff, eff)
      acks.push({ id: ev.id, eff })
    }
    if (minEff < this.head.eff) this.rewindFrom(minEff)   // перемотка шкал
    else this.applyNeedsForward()
    this.maybeCheckpoint()                                 // раз в ~50 событий или в час
    this.scheduleAlarm(nextCriticalAt(this.state))         // сердечки, конец мытья, конец передержки
  })
  this.notifySockets(this.rev)                             // ПК и открытое приложение получают {t:'rev'}
  return { now: Date.now(), rev: this.rev, acks, rejected, state: this.snapshot(),
           inbox: this.inbox.since(dev.lastInboxSeen) }
}

rewindFrom(eff) {
  const cp = this.checkpoints.latestBefore(eff)            // state_json + rev
  let s = parse(cp.state)
  for (const ev of this.events.byEffFrom(cp.eff))          // ORDER BY eff, device_id, seq
    s = needsReducer(s, ev, cfgAt(ev.recv))                // только шкалы; ресурсные дельты берём сохранённые
  this.state = s
}
```

### 2.5 Сердечки и смерть (честно и детерминированно)

- `nextCriticalAt(state)` считает формулой момент следующей потери сердечка. Сервер ставит `setAlarm()`, alarm пересчитывает состояние. Работает, даже если все устройства офлайн: у DO свои часы.
- При 0 сердечек → состояние `dying(at)`, **не** `dead`. Окончательная смерть наступает, когда выполнено одно из условий:
  - все устройства владельца и активные сиделки, бывшие онлайн за 72 ч, синкнулись **после** `at` и ничего спасающего не прислали;
  - прошло 24 ч после `at`.

  Если позднее событие с `eff < at` вытягивает шкалы, перемотка снимает `dying`.
- Смерть финализирует перенос питомца в `memorial` (альбом памяти: даты, фото-кадры, шмотки, лучшие моменты). Новое яйцо — новая строка `pets`. Монеты и дом остаются у владельца.
- `admin_revive` (только по ADMIN_KEY) — на случай бага сервера, не геймплей.
- Предупреждения о смерти клиент строит **сам** по той же формуле: локальные уведомления, Live Activity, виджет. Сервер нужен только для финального решения.

### 2.6 Версионирование

| Что | Как |
|---|---|
| API | Префикс `/v1/`. Ломающие изменения → `/v2/`, старое держим, пока есть клиенты (сборки обновляются раз в 7 дней вместе с переподписью) |
| Схема события | Поле `v` у события. Сервер умеет текущую и предыдущую версию каждого типа |
| Правила симуляции | `rules` в событии и `RULES_VERSION` на сервере. Если `rules < MIN_RULES`, в ответе `minClient` → баннер «обнови» |
| Конфиг экономики | `config/economy.json` в репо с полем `version` (целое) → `npm run config:push` → новая строка в D1 `economy_config`. Отдаётся с ETag, клиент кэширует. Цены и награды берутся из версии, **активной на момент прихода**. Если клиент предсказал по старой цене, получает `rejected: price_changed` + новый конфиг. Скорости шкал меняются только с явной датой вступления (`effective_from`), чтобы перемотка прошлого не меняла историю |
| Схема DO | Таблица `meta(schema_version)`, миграции SQL прогоняются в конструкторе под `blockConcurrencyWhile` |
| Схема D1 | `migrations/NNNN_*.sql` + `wrangler d1 migrations apply` |

### 2.7 Мягкий анти-чит (друзья, но экономика не ломается)

1. **Время** — §2.3: монотонные часы, зажим `eff`, длительности по серверу.
2. **Случайность на сервере:** рулетка, капсулы, редкость дропа. Клиент только анимирует результат из ответа.
3. **Мини-игры через сессию:** `game_start` → сервер выдаёт `{sessionId, seed, startedAt}`. На `game_finish{score, durationMs}` проверяется:
   - `durationMs` ≈ серверной разнице;
   - `score ≤ maxScorePerSec(game) × duration`;
   - одна сессия = одна награда.

   Монеты по формуле из конфига с **дневным потолком по источнику**, например не больше 300 монет в день с мини-игр. Блок Дуо-дуэль: результат приходит из `DuoRoom` на сервере, а не от клиента.
4. **Шаги и привычки:**
   - `walk_steps` с потолком ~12 000 шагов в час и дневным потолком наград;
   - `habit` (автоматизации «Команд») влияет на настроение, но монеты даёт только с дневным потолком.
5. **Кошелёк — журнал** (`ledger`: дельта, источник, ссылка на событие). Баланс = сумма. Отрицательный баланс невозможен: проверка в ресурсной фазе.
6. **Аномалии не банят, а помечают:** `flags` в аналитике (много отказов `no_item`, `eff` часто зажимается, часы устройства врут больше чем на час). Смотрю раз в неделю.

## 4. Безопасность и идентичность

### 4.1 Выбор: P-256 ECDSA подпись запросов

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| HMAC (секрет в Keychain) | Проще всего, быстро | Сервер хранит секрет в открытом виде: утечка базы = можно действовать от имени всех. При привязке секрет надо передавать | Нет |
| Ed25519 | Короткие ключи, быстро, есть в WebCrypto Workers и CryptoKit | Secure Enclave его не умеет; на Windows нужна библиотека | Нет |
| **P-256 ECDSA (ES256)** | CryptoKit `P256.Signing`, **по желанию Secure Enclave** (ключ не извлекается); Windows `ECDsa`/CNG из коробки; WebCrypto в Workers; формат подписи r‖s 64 байта у CryptoKit `.rawRepresentation`, .NET `SignData` и WebCrypto совпадает | Чуть длиннее ключи | **Да** |

**Уточнения:**
- **Хранение на iOS:** программный ключ CryptoKit в Keychain с `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, чтобы фоновые задачи и интенты подписывали при заблокированном экране. Secure Enclave — опционально, после проб.
- **Виджету ключ не нужен:** у него W-токен. Это снимает зависимость от общего Keychain access group при бесплатной подписи.
- **Интенты Live Activity и виджета** не ходят в сеть сами. Они кладут событие в общий outbox (App Group), отправляет приложение. Если App Group не работает, интент в процессе приложения (`LiveActivityIntent` исполняется в приложении) отправляет сам.

### 4.2 Подпись запроса

```
Заголовки: X-Pet-Account, X-Pet-Device, X-Pet-Ts (мс, по серверному offset), X-Pet-Sig (base64url r||s)
Строка:    "PET1\n" + METHOD + "\n" + PATH?QUERY + "\n" + TS + "\n" + base64url(SHA256(body))
```

```ts
// Account DO: проверка (псевдокод)
async auth(req) {
  const dev = this.sql`SELECT pubkey, revoked FROM devices WHERE id = ${hdr.device}`.one()
  if (!dev || dev.revoked) return 401
  if (Math.abs(Date.now() - hdr.ts) > 5 * 60_000) return 401 + { now: Date.now() }   // клиент пересчитает offset и повторит
  const key = this.keyCache.get(dev.id) ?? await crypto.subtle.importKey('raw', dev.pubkey,
              { name: 'ECDSA', namedCurve: 'P-256' }, false, ['verify'])
  const ok  = await crypto.subtle.verify({ name: 'ECDSA', hash: 'SHA-256' }, key, sig, canonical(req, bodyHash))
  if (!ok) return 401
}
```

**Защита от повторов:**
- окно ±5 мин;
- **все изменяющие операции идемпотентны**: события по `deviceId:seq`, подарки по `idem`, игровые сессии одноразовые, ссылки привязки одноразовые.

Повтор перехваченного запроса ничего не меняет, поэтому таблица nonce не нужна. Перехват при HTTPS и так маловероятен.

### 4.3 Остальное

- **Регистрация по инвайт-коду** (`wrangler secret put INVITE_CODE`, один на всех друзей, можно сменить). Без него кто угодно наплодит аккаунты и съест лимиты.
- **Код восстановления** (20 символов Crockford base32) показывается один раз при регистрации, «сохрани в Заметки». На сервере хранится только хэш. Актуально при бесплатной подписи: если приложение переустановится с другим bundle id или team, Keychain потеряется.
- **Код друга:** 8 символов Crockford base32 (`K7MQ-2XA9`), отдельный от accountId, можно перевыпустить.
- **Поиск по имени:** только у тех, кто включил `discoverable`. Результат — заявка, не дружба.
- **Друзья видят только `public_profile`:** имя, персонаж, шмотки, уровень, дом, альбом. Устройства, ключи, кошелёк, аналитика закрыты.
- **Лимиты частоты:** счётчики в DO (тык, подарки, поиск, попытки recovery) + `/v1/register` ограничен инвайтом. Дополнительно можно включить Rate Limiting binding Workers.
- **Секреты:** `ADMIN_KEY`, `INVITE_CODE` через `wrangler secret put`, не в репо. В `wrangler.toml` только несекретные vars.
- **Бэкап:**
  - D1 Time Travel, 7 дней на Free;
  - DO: раз в сутки alarm копирует снапшот каждого питомца в D1 `pet_backups` (последние 7). Это страховка от бага, который «убил» питомца. Point-in-time recovery для SQLite DO проверить отдельно.

## 5. Ассеты своих персонажей и шмоток

### 5.1 Модель хранения

- **Content-addressed:** файл = `sha256` его содержимого. Изменился файл — новый адрес. Клиенты кэшируют навсегда (App Group, ПК — локальная папка), повторно не качают.
- **Манифест персонажа** (в DO владельца, публичная копия в D1 для друзей):

```jsonc
{ "id": "tung_v2", "name": "Тунг тунг сахур", "skeleton": "pet-rig-v1", "ver": 3, "author": "<accountId>",
  "files": { "glb": "sha…", "usdz": "sha…",
             "frames": { "small": "sha…", "medium": "sha…", "island": "sha…" } },   // спрайт-листы для виджета/острова
  "bytes": 1840000 }
```

Шмотка — такой же манифест: `slot` (кость), `glb`/`usdz`, превью-кадр. Одна шапка на всех держится за счёт общего скелета, это зона исследования ассетов.

### 5.2 Целевые размеры

| Ассет | Цель | Почему |
|---|---|---|
| Персонаж `.glb` | ≤ 1 МБ (≤ 3–5 тыс. треугольников, текстуры 128–256 px) | PS2-лук и так требует мыльных маленьких текстур |
| Персонаж `.usdz` (iOS) | ≤ 1,5 МБ | Конвертация на ПК или в CI (Blender CLI), не на сервере |
| Спрайт-лист для виджета | ≤ 300 КБ на размер | У виджет-расширения жёсткий лимит памяти (~30 МБ) |
| Кадры для острова | ≤ 100 КБ | Крошечная область |
| Шмотка | ≤ 150 КБ | — |
| Итого на 10 человек × 5 персонажей × ~3 МБ + шмотки | **~200 МБ** | Влезает и в KV (1 ГБ), и в R2 (10 ГБ) |

### 5.3 Где лежит

| Что | Где | Почему |
|---|---|---|
| Встроенные персонажи, шмотки рынка, кадры | **Статика Worker'а** (`server/public/assets/<sha>`), деплой вместе с кодом | Бесплатно, файл до 25 МиБ, без отдельного сервиса. Для ускорения можно класть и в бандл приложения |
| Загруженные своими (через «Файлы» на телефоне или с ПК) | **R2 bucket `pet-assets`**, если к аккаунту CF привязана карта | 10 ГБ, 1 млн операций класса A и 10 млн класса B в месяц, исходящий трафик бесплатно |
| То же, если карты нет | **KV namespace `ASSETS_KV`**, ключ `a/<sha>` | 25 МиБ на значение, 1 ГБ, 1 000 записей в день (загрузок мало) |

**R2 и карта.** По сторонним гайдам 2025–2026 Cloudflare просит привязать платёжный метод при первом включении R2, хотя в пределах free tier не списывает. В официальном прайсинге это не сказано. **Проверить в дашборде** (R2 → Overview). Решение: код пишем через интерфейс `AssetStore { get(sha), put(sha, bytes) }` с двумя реализациями, бэкенд выбирается конфигом. Стартуем с KV, переезд — скрипт копирования.

**Поток «свой персонаж».**
1. Импорт `.glb` на телефоне или ПК.
2. Клиент считает sha → `PUT /v1/assets/{sha}` → `PUT /v1/characters`.
3. `usdz` и кадры для виджета появляются после прогона пайплайна на ПК / в CI (Blender CLI). Пайплайн докладывает файлы теми же PUT и поднимает `ver` манифеста.
4. Друг видит гостя: тянет манифест → недостающие sha → кэш.

## 7. Риски

| # | Риск | Вероятность / вред | Что делаем |
|---|---|---|---|
| 1 | **Дневные лимиты общие на аккаунт** (Блок Дуо, будущие воркеры). Ошибка «WebSocket через `accept()`» съедает duration | Средн. / сервер лежит до 00:00 UTC | Только Hibernation API; офлайн-первый клиент переживает простой; раз в неделю смотрим Usage в дашборде; запасной путь — $5/мес Paid |
| 2 | **R2 требует карту** | Высок. / нет R2 | KV-бэкенд по умолчанию, интерфейс `AssetStore` |
| 3 | **Расхождение симуляции** Swift ↔ TS ↔ ПК | Средн. / «прыгающие» шкалы после синка | Целочисленная математика, golden-векторы в CI обеих сторон, сервер всегда прав; запасной путь — JS-ядро через JavaScriptCore |
| 4 | **App Groups / Keychain при бесплатной подписи** не делятся с расширением | Средн. / виджет не видит стейт и ключ | W-токен вместо ключа, ввод в настройке виджета; интенты отправляют из процесса приложения (проверяет res-signing) |
| 5 | **Потеря Keychain** при переустановке, смене bundle id или переподписи | Средн. / «чужой» новый аккаунт | Код восстановления; привязка с ПК, если ПК жив |
| 6 | **Подкрутка часов + перезагрузка** (сбрасывает монотонный якорь) | Низк. / мелкая выгода | Зажим `eff` между прошлым синком и приходом, `MAX_BACKDATE`, длительности по серверу, флаги аномалий |
| 7 | **Смерть из-за бага сервера** или пересчёта | Низк. / очень обидно (смерть навсегда) | `dying` с окном оправданий, бэкапы снапшотов в D1, `admin_revive` |
| 8 | **Рост журнала** до 1 ГБ на DO (Free) | Низк. | Компактизация старше 30 дней, чекпойнты |
| 9 | **Доступ к `*.workers.dev` из РФ** у друзей (бывают блокировки и замедления) | Средн. для друзей в РФ / нет синка | Офлайн-первый режим; если подтвердится — свой домен на Cloudflare (Workers Custom Domain), это бесплатно при домене в CF |
| 10 | **Cache API не работает на `workers.dev`** | — / просто нет edge-кэша | Не полагаемся на него; ETag/304 и кэш isolate'а для конфига |
| 11 | **Расхождения в доках CF** (1 ГБ vs 10 ГБ на DO на Free) | Низк. | Планируем по меньшему |
| 12 | **Ощущение «мёртвой» социалки** без пушей | Высок. / главный риск по ощущениям | Инбокс в каждом sync, «почтальон», «📬» в виджете, отметки «увидел», живой WebSocket на ПК, частый reload виджета в окна активности; локальные уведомления после фонового синка с новыми письмами |
